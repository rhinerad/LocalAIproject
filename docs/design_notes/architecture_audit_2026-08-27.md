# local_agent/ — architecture audit

*2026-08-27. Static-code audit: every module below was read in full, not sampled or summarized from filenames. Every count is grep- or AST-verified against the current tree, not estimated. Where a claim could not be verified by reading code (e.g. concurrent-access behavior under real load), it is marked unverified rather than asserted — the project's own standard for evidence, applied here to the audit itself.*

*Scope note: an external architecture review already happened once, on 2026-08-24 (`docs/design_notes/architecture_review_response.md`). Its five accepted items became UPGRADE 12, which is still unbuilt. This audit does not repeat those five items; it looks at what that review missed, plus what has changed since.*

## System at a glance

`local_agent/` is no longer a small chat wrapper. Excluding the vendored Sideband/Reticulum source tree, it is **~50 top-level modules totaling 13,333 lines**, plus **51 test files totaling 4,753 lines**. It has grown across 23 sequential numbered upgrade prompts, most implemented by a different agent session than the one before it. That history is visible in the code: several of the findings below are exactly the shape you'd expect from independently-scoped upgrades landing in the same files without a shared abstraction being extracted afterward.

Two fan-in numbers matter for everything that follows: **13 modules import `router.py` directly**, and **3 import `tools.py`** (`agent.py`, `agentic_eval.py`, `server.py`). `router.py` is the de facto hub of the system; `tools.py` is not, because its role is a registry consumed almost entirely through one function, `call()`.

## 1. Multimodal orchestration ↔ structured tool-calling pipeline

**What's solid.** `tools.call()` (tools.py:1787–1824) is a genuinely well-built chokepoint: it checks the tool exists, checks `ToolContext.permits()`, injects trusted fields the model can never forge (`__remote_render_identity`, `__remote_schedule_identity`) only from server-side context, audits every call through `remote_security.audit_tool()`, and converts every exception into a uniform `ERROR:` string rather than crashing the turn. `capabilities.py`'s gate-with-reason pattern (`{"available": bool, "reason": str, "install": str, "size": str}`) is applied consistently across every sensory tool. This part of the system is not the risk.

**The risk is `agent.answer()`.** It is one function, agent.py:671–1047, ~377 lines, and it is where every subsystem in the project actually meets: routing (`router.decide()`), GPU permission gating (`gpu_gate.request()`), task checkpointing (`agentic_state`), URL prefetch, project-doc retrieval prefetch, prior-chat retrieval prefetch, difficulty-based model escalation, exemplar prefetch, context trimming, the primary→fallback retry, legacy tool-call parsing, and the actual multi-hop tool loop — all interleaved by direct, sequential mutation of a shared `msgs` list and a shared `emit()` callback. There is no seam between "decide what context the model needs" and "run the model" and "enforce permissions." A change to any one of those eight concerns touches the same function.

A concrete symptom of the same pressure: **eight compiled regexes at module level** (`_START_CURRENT_RENDER_RE`, `_STOP_COMFYUI_RE`, `_ACCESS_BYPASS_RE`, `_UNVERIFIED_EXECUTION_RE`, `PROJECT_CONTEXT_RE`, `_PROJECT_MEMORY_LINE_RE`, `URL_RE`, `TOOL_RE`) implement a second, deterministic router that runs *before* the model ever sees the request, specifically for actions where the model's tool selection isn't trusted — starting a render, stopping ComfyUI, refusing an access-bypass request. This isn't a stylistic choice; it's evidenced necessity. `CHANGELOG/2026-08-27_optional_dep_guards_and_scheduler_live_pending.md` records the model choosing `start_current_chat_render` over `schedule_phone_messages` **for 26 consecutive messages** in one real conversation, because the tool description didn't say clearly enough "this is not rendering." The fix that day was a tool-description edit, not a structural one. That pattern — patch the description, add a regex escape hatch — doesn't scale linearly as more must-not-get-wrong tools are added; each one needs its own hand-authored classifier bolted onto `agent.py`.

A second symptom: **five independently-tuned context-budget constants** (`MAX_TOOL_RESULT_CONTEXT_CHARS`, `MAX_URL_EVIDENCE_CHARS`, `MAX_EXEMPLAR_CONTEXT_CHARS`, `DEEP_RESEARCH_RESULT_CONTEXT_CHARS`, `MAX_CONTINUITY_TURN_CHARS`) govern five separate "inject relevant context into `msgs`" code paths (`add_supplied_url_evidence`, `_prefetch_requested_project_evidence`, the inline `chat_retrieval` block, the inline difficulty-escalation block, `_prefetch_approved_exemplars`), each hand-rolled rather than expressed as one budget policy with named sources.

The media pipeline (`media_queue.py` + `media_watcher.py` + `capabilities.py` + `router.py`) is architecturally cleaner: it's a genuinely separate polling/state-machine layer (`pending/processing/done/failed/cancelled` directories, atomic job files, a single-instance watcher lock) that the chat loop only touches indirectly, by enqueuing and checking a `{"queued": true}` sentinel in the tool result. That decoupling is a real strength — but it also means "integration" here is two loosely-coupled polling systems synchronized through JSON files and sentinel values, not a single event-driven path. Worth naming as a deliberate tradeoff, not a defect: it keeps the watcher's GPU/VRAM logic out of the request path, at the cost of every caller needing to understand the `{"queued": ...}` convention.

The legacy `TOOL: name {json}` text-parsing fallback (`parse_tool`, `TOOL_RE`) is still live in the hop loop even though native function calling shipped in UPGRADE 01. This is not untested dead weight — `test_native_tool_calling.py` has two tests specifically for it (`test_legacy_fallback_logs_and_runs`, `test_malformed_legacy_json_never_runs_tool`) — but it is a second parsing path maintained for models that, per `router.py`'s own comment, are no longer part of the permitted model roster ("the Huihui pair is the only permitted conversation-model family"). Worth a deliberate decision (keep for future model flexibility vs. remove), not an oversight to flag as broken.

## 2. Chroma DB memory persistence

**Correct the premise first.** Chroma is not the project's memory system; it's one of **four independent, non-communicating retrieval/memory subsystems**, each with its own storage format, its own relevance-scoring math, and its own dedup strategy:

| subsystem | file(s) | storage | scoring | gated by |
|---|---|---|---|---|
| operator facts | `memory.py` (133 lines) | flat JSON, byte-capped | none (priority sort) | explicit "remember that…" |
| project docs | `retrieval.py` (360 lines) | JSON chunk index, mtime-keyed | BM25 (custom, ~35 lines) | none — read-only |
| prior chats | `chat_retrieval.py` (50 lines) | reads `store.py` JSON | term-overlap / √length (not BM25) | none — read-only |
| approved exemplars | `exemplar_embeddings.py` (200 lines) + curator/filter/lifecycle (334 lines) | Chroma `PersistentClient` | cosine similarity | human approval queue |

That's roughly 1,077 lines solving overlapping "find relevant context for this turn" problems four different ways, each independently reimplemented rather than sharing an interface. `retrieval.py` was in fact built with exactly this kind of extension in mind (`ScorerProtocol`, a stubbed `EmbeddingScorer` placeholder for a future embedding model) — but `chat_retrieval.py` and `exemplar_embeddings.py` didn't grow into that interface; they're separate code with separate math.

**The Chroma-specific code itself is careful.** Telemetry is explicitly disabled (`anonymized_telemetry=False`), the collection is created with the correct `hnsw:space: cosine` for normalized embeddings, writes to the JSON sidecar records use the same atomic tmp-then-replace pattern as the rest of the project, and — as of today, `CHANGELOG/2026-08-27_optional_dep_guards_and_scheduler_live_pending.md` — the two bare `import chromadb` statements are now guarded, with `agent.py`/`server.py` confirmed (by that entry's own test run) to still import when chromadb is absent. I re-read the current `exemplar_embeddings.py` directly rather than trusting the changelog claim: the guard is in place exactly as described.

**The actual efficiency issue:** `_client()` (exemplar_embeddings.py:51–57) constructs a brand-new `chromadb.PersistentClient` on *every* call, with no caching or pooling — even though the module already demonstrates it knows how to hold a module-level singleton correctly, for the unrelated background-worker thread (`_WORKER`/`_WORKER_LOCK`). `_collection()` calls `_client()` fresh every time it's invoked, and it's invoked from three separate call sites: `semantic_duplicate()`, `embed_record()`, and — worse — inside `retrieve()`'s own list comprehension (`exemplar_embeddings.py:108`), which opens **one fresh `PersistentClient` per requested category, per call**. A single `retrieve()` across two categories opens Chroma twice. This isn't just a background-thread cost either: `exemplar_filter.check_candidate()` calls `semantic_duplicate()` synchronously during staging, and `exemplar_curator.review()`'s approve path calls `embed_record()` synchronously at review time — so an operator clicking "approve" in the GUI pays this cost inline, not just the 20-second background poll.

**An unverified concurrency risk, flagged as a risk, not a bug:** the background `_worker()` thread (polling every 20s) and the inline request-path calls above can each open an independent `PersistentClient` handle against the same on-disk `exemplar_store/chroma` directory at the same time. Nothing coordinates them the way `_WORKER_LOCK` coordinates thread startup. I have not reproduced a failure — this would need to be exercised under real concurrent load to confirm one way or the other — but it's the kind of gap worth closing before this subsystem sees more traffic, and it's cheap to close by fixing the client-caching issue above at the same time.

## 3. CPU/GPU dynamic resource routing

**What's solid, and should stay exactly as it is:** the three-signal, fail-safe busy detection in `gpu_busy()` (router.py:387–428) — queue-owner file, port 8188, `nvidia-smi` — with the explicit rule that an unreadable `nvidia-smi` counts as busy, not idle. This is well-reasoned and well-commented; nothing here needs refactoring, and I'd flag any future change to loosen it as a regression, not a cleanup.

**The maintainability problem is that `router.py` has become a second god-module**, 795 lines, imported directly by 13 other files, carrying at least six originally-separate concerns that arrived through different upgrades: basic tier selection, adaptive 14B↔8B context-based switching (UPGRADE 10), reactive OOM retry, coding-model routing (a later, parallel addition), vision/media VRAM arbitration (`plan_vision_vram`, UPGRADE 15), and cross-process signaling (`chat_busy`, `media_pressure`). `decide()` alone (router.py:547–723) is ~177 lines with deeply nested conditional branches.

The clearest concrete evidence of accreted-rather-than-designed complexity: `decide()` contains **two near-duplicate fallback blocks** — one for the primary-reasoning-pair CPU handoff (router.py:687–697) and one for the coding-model CPU handoff (router.py:698–717) — that resolve a paired CPU fallback, decide whether to reuse the CPU-tier store or fall back to the GPU-tier store with `num_gpu=0`, and build an explanatory `why` string, in near-identical shape, twice. This reads exactly like the coding-model routing was added by copying the reasoning-pair logic and adapting it in place, rather than extracting the shared "paired-model CPU fallback" behavior into one parameterized helper both cases call.

**A specific, verifiable instance of config drift**, the same failure class this project's own `CLAUDE.md` singles out as its worst historical bug (the `sync_omni_audio_config.py --check` drift): `num_ctx: 16384` is defined independently in three places — `router.py`'s `CPU_OPTIONS` (router.py:221), `router.py`'s `GPU_OPTIONS` base default (router.py:223, before `Decision.options()` conditionally overrides it for GPU), and `ollama_client.py`'s `DEFAULT_OPTIONS` (ollama_client.py:52). The third copy carries a comment — *"Keep this in sync with router.CPU_OPTIONS... 8k makes a CPU fallback fail before it can consider the operator's request"* — that is itself the tell: the project already knows this value must not drift, and the only enforcement mechanism is a comment asking a future editor to remember. There is no shared constant, and no test asserts the two stay equal.

**Test coverage is a genuine mitigating factor.** `router.py`'s core decision logic has real regression coverage — `test_router_switching.py` (20 tests), plus `test_vram_arbitration.py` (5 tests) — and `agent.py`'s tool-calling loop has 27 tests in `test_native_tool_calling.py`. That materially lowers the risk of decomposing either file: a refactor has something to run against. `exemplar_embeddings.py`, by contrast, has only 2 tests across 53 lines relative to its complexity — the module carrying the least test weight is also the one with the client-caching issue above, which is a reason to sequence work there with a test written first.

## Cross-cutting findings

**The tmp-then-replace atomic-write pattern is independently reimplemented in 14 files** (`agentic_state.py`, `exemplar_curator.py`, `exemplar_embeddings.py`, `exemplar_lifecycle.py`, `gpu_gate.py`, `learning.py`, `media_queue.py`, `media_watcher.py`, `memory.py`, `phone_scheduler.py`, `remote_security.py`, `retrieval.py`, `router.py`, `store.py`) — verified by grep, not estimated. Each defines its own private helper for the same three-line body, under four different names (`_atomic`, `_save`, `_write_atomic`, `_atomic_write` — only `feedback_manager.py` uses that last name, and nothing imports it from there). Every individual copy looks correct; the risk is that a future correctness fix (a Windows-specific lock issue, for instance) gets made in one copy and not the other thirteen. This is the single cheapest, lowest-risk item in this whole audit to fix.

**Status documentation has already drifted once, verifiably.** `local_agent/UPGRADE/BUILD_STATUS.md` opens with its own banner admitting it's superseded by `docs/LOCAL_AGENT_CURRENT_HANDOFF_2026-08-26.md`. A concrete instance found while reading, not inferred: `00_INDEX.md` row 12 lists *"a `propose_file_diff` review tool"* as still-pending, unbuilt work — but `propose_file_diff` is fully implemented and registered in `tools.py` right now (tools.py:772–793, schema at 1519). The tool shipped; the planning doc tracking it didn't get updated. With four separate documents claiming to describe "current state" (`00_INDEX.md`, `BUILD_STATUS.md`, the canonical handoff doc, `CHANGELOG/README.md`), this kind of drift is structural, not a one-off mistake — there's no single place status is written once and read everywhere else.

## Prioritized recommendations

Ordered by risk-reduced-per-effort-spent, not by subsystem. Nothing here has been implemented; this is the list to work from when you're ready.

1. **Extract one shared `atomic_write(path, data)` helper and migrate the 14 call sites.** Lowest risk, smallest diff, removes a real (if currently dormant) correctness hazard, and every migrated file already has whatever tests currently exercise its save path — a natural first PR.
2. **Cache the Chroma `PersistentClient` as a module-level singleton in `exemplar_embeddings.py`**, guarded the same way `_WORKER`/`_WORKER_LOCK` already is. Write the concurrency test *first* (background worker + inline approve-path call racing against the same store) before changing the client lifecycle, since that's the one claim in this audit that's flagged unverified rather than confirmed.
3. **Give `router.py`'s duplicated primary/coding fallback logic in `decide()` one shared helper.** `test_router_switching.py`'s 20 tests make this a genuinely safe extraction, not a leap of faith — run them red/green before and after.
4. **Replace the three independent `num_ctx=16384` literals with one imported constant**, and add the one-line test that was missing: assert `ollama_client.DEFAULT_OPTIONS["num_ctx"] == router.CPU_OPTIONS["num_ctx"]`, so drift fails CI instead of waiting for a comment to be remembered.
5. **Decompose `agent.answer()`'s prefetch stage** — pull the five independent context-injection blocks (URL evidence, project-doc retrieval, chat retrieval, difficulty escalation, exemplar retrieval) behind one small `ContextPrefetcher` interface with a single named budget policy, even if the call order inside `answer()` stays the same at first. This is the highest-value, highest-effort item, and the one most worth doing only after 1–4 establish the pattern of "extract, keep the existing tests green."
6. **Pick one home for "what's built" and make the other docs point to it, not repeat it.** Not a code change, but the `propose_file_diff` example shows this is already producing wrong operator-facing claims, and it will keep happening as long as four files independently track the same fact.
7. **Longer-horizon, not urgent:** consider whether `chat_retrieval.py`'s bespoke scorer should be replaced by a call into `retrieval.py`'s existing `ScorerProtocol`/`LexicalScorer`, since that interface was explicitly built to be reused and currently isn't. Lower priority than 1–6 because `chat_retrieval.py` is small (50 lines) and low-traffic; worth doing opportunistically rather than as its own project.

Items 5 and the still-open UPGRADE 12 (keep-alive, quantized KV cache, mid-job pre-emption, queue priority) touch adjacent code — worth sequencing together rather than as competing efforts.
