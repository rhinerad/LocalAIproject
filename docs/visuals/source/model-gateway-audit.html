LocalAIproject · Phase 1 audit + Phase 2 proposal · 2026-11-02

Model Gateway Audit

How the agent's LLM calls are wired today, what a hybrid Ollama + Anthropic router has to preserve, and which of the two designs fits this codebase.

Recommendation: Option B, native middleware inside the existing router seam. The codebase already has a backend abstraction (Decision.backend is "ollama" | "powerinfer" | "farm") and a complexity classifier (classify_capability → CAP_LOGIC). Adding "anthropic" as a fourth backend reuses both, keeps the VRAM and thermal guards exactly where they are, needs no extra port or process, and is testable with the same patch.object(router, …) pattern as the 118 existing router tests. A LiteLLM proxy would force a rewrite of the Ollama client onto the OpenAI wire format, which is where the project's VRAM knobs (num_gpu, num_ctx, keep_alive, think) live. For goal 2 (CLI tooling against local models) no gateway is needed at all: Ollama v0.14+ serves the Anthropic Messages endpoint natively.
Two things you need to decide before Phase 3. (1) The code is not on the designated branch. claude/jolly-dirac-9impbq and main contain only a README; the whole agent lives on claude/zealous-johnson-g4xoz1 (8 commits, 2,461 tracked files). I audited that branch read-only in a scratch worktree. (2) local_agent/README.md line 142 states a standing rule: "No cloud AI accounts or cloud model calls." This task reverses that rule for one tier. The README and the Claude Code deny list (which blocks reading .env) should be amended in the same change so future agents are not working against contradictory instructions.

1. The analogy: a taxi dispatcher with two garages

Think of router.py as a dispatcher sitting in front of a single parking spot (the RTX 5080's 16 GB of VRAM). Before every ride it radios three questions: is a render truck parked there (render_queue_owner.json), is ComfyUI's engine running (port 8188 listening), is anything else on the card (nvidia-smi)? If any answer is yes, it sends the ride to the slow CPU cab on port 11435 and, crucially, tells its own GPU cab to leave the spot (keep_alive: 0). If no, the big 14B cab on port 11434 takes the ride.

What you are asking for is a third garage: a long-distance partner carrier (Anthropic) that never needs the parking spot at all. Option A hires a separate dispatch company (LiteLLM) and puts it between you and every garage, on its own radio protocol. Option B gives the existing dispatcher one more phone number. The audit below is about which of those keeps the parking-spot rules intact.

4. VRAM safety: why cloud calls cannot collide with ComfyUI

Back to the parking spot. The question is whether a cloud-bound request could ever cause Ollama to pull a model into VRAM while ComfyUI is rendering. Reading the call graph: VRAM only changes in two ways.

  • Loads happen exclusively when a request body hits http://127.0.0.1:11434/api/chat (or /api/generate without keep_alive: 0). Nothing else in the tree loads a model.
  • Evictions happen via keep_alive: 0 in unload(), prepare_gpu_model(), evict_gpu_residents(), and _finish_gpu_ollama(ensure_gpu_evicted=True). These free VRAM; they never claim it.

So the invariant for the gateway is simple to state and simple to test: a Decision with backend="anthropic" is returned from decide() before any _finish_gpu_ollama / prepare_gpu_model call, and ollama_client dispatches it to the Anthropic client without constructing a /api/chat request. The existing busy probes still run first (they are read-only and cheap), which is useful: when ComfyUI is rendering, the cloud tier becomes the preferred path for heavy turns instead of the CPU 8B, which is a real quality win during renders.

One subtlety worth keeping: decide() skips the GPU inventory probe entirely when the GPU is busy and the CPU 8B exists (skip_gpu_inventory, router.py:1655-1660). The cloud branch should sit after that check so a render never accumulates failed loopback requests.

5. Option A vs Option B

Option A · LiteLLM proxy on :4000

separate process · OpenAI wire · YAML aliases

  • Pro: declarative aliases (tier-local-fast, tier-cloud-heavy), built-in fallbacks, spend logging, one endpoint any OpenAI-speaking tool can hit.
  • Con: LiteLLM speaks OpenAI chat-completions, not Ollama's native /api/chat. ollama_client.py would have to be rewritten, and num_gpu, num_ctx, keep_alive, think become per-model YAML settings rather than per-turn router decisions. The adaptive 14B↔8B context switch and the keep_alive:0 yield-on-render both depend on per-turn control.
  • Con: second long-running process to start, health-check, and keep off the GPU; 100+ pip packages against a stdlib-only project.
  • Con: routing by prompt complexity is not a LiteLLM primitive; the agent would still have to pick the alias per turn, so the classifier logic lives in router.py anyway.

Option B · native backend in router.py

no new port · official anthropic SDK · same test harness

  • Pro: reuses the existing seams (F3, F4). The change is one new Decision branch plus one adapter module; agent.py's streaming loop sees the same str / ToolCall / StreamEnd objects.
  • Pro: VRAM rules stay in one file and keep their 118 tests. The cloud invariant (section 4) is a three-line unit test.
  • Pro: offline fallback is explicit: catch APIConnectionError / RateLimitError → re-decide with skip_cloud=True, same shape as fallback_after_primary_failure().
  • Pro: the official SDK gives typed errors, retries, prompt caching, structured outputs, and streaming without a shim.
  • Con: no out-of-process endpoint for other tools. If a second consumer appears later, a thin FastAPI front can be bolted onto the same adapter. Not needed now (see goal 2).
  • Con: adds anthropic + httpx + pydantic + anyio to a stdlib-only tree (roughly 15 MB of wheels). Needs your download approval.

6. Goal 2: CLI tooling against local models

This needs no gateway. Ollama v0.14 and later serve the Anthropic Messages endpoint (/v1/messages) natively, with streaming, system prompts, and tool calling; the workstation runs 0.32.15. Claude Code is pointed at it with two variables (the token is accepted but not validated):

# PowerShell, offline coding session against the GPU server
$env:ANTHROPIC_BASE_URL  = "http://127.0.0.1:11434"
$env:ANTHROPIC_AUTH_TOKEN = "ollama"
$env:ANTHROPIC_MODEL      = "josiefied-qwen2.5-coder-14b:q4_k_m"
claude

# Or the CPU server, so a render is never disturbed
$env:ANTHROPIC_BASE_URL  = "http://127.0.0.1:11435"

Two cautions from the docs: tool_choice and count_tokens are not supported on Ollama's endpoint, and pointing Claude Code at 11434 does load that model into VRAM, so the same "is 8188 listening" check applies before an offline coding session starts. The Phase 3 start script can print that check.

8. Decisions (approved)

  1. Branch. Build model_gateway/ on top of claude/zealous-johnson-g4xoz1 (where the code is), pushed to the designated claude/jolly-dirac-9impbq? That means resetting jolly-dirac to zealous-johnson's head first. Or keep it standalone on jolly-dirac as it is today, importing nothing from local_agent/?
  2. Dependency. Approve installing the official anthropic Python SDK (about 15 MB with httpx/pydantic/anyio)? The alternative is a stdlib urllib client against /v1/messages, which works but loses typed errors, retries, and streaming helpers.
  3. Models. claude-opus-5-5 for the heavy tier and claude-sonnet-5-5 for the busy-GPU tier, as above? Or Opus only?
  4. Eligibility. Cloud only for unpinned CAP_LOGIC turns plus an explicit operator pin, with compactor / memory / planner hard-excluded? Or also CAP_CODE turns while ComfyUI renders?
  5. Rule change. Amend local_agent/README.md line 142 to read "cloud model calls only through the gateway's cloud tier, off by default (MODEL_GATEWAY_CLOUD=0)" in the same change?
  6. Offline behaviour. On connection failure, fall back silently to the local tier the router would have chosen, with a status-badge note? Or surface it and let you decide per turn?
