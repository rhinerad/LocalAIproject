# Equal Shares — human guide

Plain-language orientation. No commands required to read this.

## What the project is

A roughly twenty-one minute film called *Equal Shares*, built as 124 short clips generated by a local video model (MiniMax H3) running inside ComfyUI on your machine. Each clip is rendered from a first frame, sometimes a last frame, and a written prompt. When all 124 are generated and approved, they get stitched together with a pre-made dialogue track and a continuous music score into a single 1344×768 master file.

The model produces its own speech and music. All of it is thrown away. The real dialogue and score are separate WAV files added at the end.

## Where things are right now

The renderer is running. It has produced 77 of 124 clips and is working through the nineteenth scene. At roughly eight minutes per clip, the remaining 47 clips are about six hours of unattended work.

The bottleneck is not rendering — it is **watching**. Only 43 clips have actually been watched and approved, up through `09C`. About 34 finished clips are sitting unreviewed. The renderer's progress counter says "valid," which only means the file came out the right length and format. It does not mean anyone has confirmed the people in it have the right faces and hands.

That gap matters, because clips are chained: the last frame of one often becomes the first frame of the next. If clip 11 turns out to be wrong, clips built on top of it may have to be redone too. The longer generation runs ahead of review, the more expensive a problem becomes when it surfaces.

## The one thing that can break the project

**Two renderers must never run at once.**

The video model needs the entire graphics card. Only one program can use the ComfyUI address (port 8188). If a second renderer starts, either it crashes, or the first one crashes, or — worst case — both write to the same progress file and the record of what's been done becomes unreliable.

This is a live risk right now for a specific reason. There are two copies of the project on disk: the original folder, and this handoff folder. The handoff folder was supposed to be a backup copy, updated once a minute. That copying process stopped at 2:22 AM on August 10. Since then the renderer has been working directly in the *handoff* folder, while the original sits frozen at 44 clips.

The older documentation still says the original folder is the real one. It isn't anymore. Anyone — a person or an AI assistant — who reads that older documentation and starts the renderer in the original folder will start a second renderer. That is exactly the collision to avoid.

**So: this folder, `COMFYUI_STORY_HANDOFF_2026-08-09`, is the real one.** The folder above it is stale. `SYNC_STATUS.json` is stale too — ignore what it says.

## How to check whether the renderer is alive

Open `outputs\equal_shares\runtime\render_supervisor.log` and look at the last line. It has a timestamp. If that timestamp is within the last ten minutes or so, it's running fine. If it's hours old, it stopped.

A healthy log looks like a repeating cycle: started ComfyUI, API ready, stopped and cleared, progress N of 124, started again. Roughly eight minutes per loop.

## What each assistant is for

**Claude Desktop** reads and writes files but cannot touch your graphics card or start programs. Use it for reviewing clips, planning fixes, and keeping documents accurate. It cannot cause a two-renderer collision. Paste `CLAUDE_DESKTOP_PROMPT.md`.

**Claude Code** can run programs on your machine. It's the most capable and the only one that can cause the collision. `CLAUDE_CODE_PROMPT.md` and `CLAUDE.md` tell it to check for a running renderer before starting anything.

**Aider** makes surgical edits to the code and settings files. `AIDER_PROMPT.md` explains what's safe to edit while a render is in flight.

If two assistants are open at once, only one of them should be allowed to run programs. The others stay read-only.

## The rules nobody may break

The full-quality model only — there's a faster "Turbo" version installed and it is forbidden, because it produces visibly worse footage. Twenty steps per clip, always.

Nothing gets deleted. Every attempt, including rejected ones, stays on disk under `A:\Users\rhine\ComfyUI-Shared\output\story\`. Rejection is recorded, not erased.

Certain story details are locked and can't drift: in the opening waiting room there is exactly one woman (the receptionist, who stays behind her window), exactly two male visitors, one chair on the left, no glass barrier of any kind, and no third man. The Narrator never looks like Kent. And in clip `04C`, Kent has already refused before the shot begins — he must never be seen taking out money or reaching toward the collection plate.

Bad audio is never a reason to reject a clip, since the audio is discarded anyway.

Sharpening or upscaling a clip cannot fix a wrong face, a melted hand, or a person turning into someone else mid-shot. Those need regenerating or cutting.

## What to do next, in order

First, decide the two-folder question is settled: this folder is canonical, the one above is a frozen snapshot. That's mostly a documentation fix, and `PROJECT_CONTINUATION_BRIEF.md` already records it.

Second, catch up on watching. Roughly 34 clips between `09C` and `18D` need a real look. Consider pausing the renderer at a clean clip boundary so review can catch up before generating deeper into the film.

Third, let the render finish the remaining 47 clips.

Fourth, run the finalizer and the completion audit. The project is not done until that audit passes every check — 124 approved clips, every original preserved, and a master file of the right size, format, and length.
