# Build spec: show review images/video inline in the local-agent GUI, and announce completions even after the turn has ended

**For:** a Claude Code session (Opus 5.5 at `xhigh`, or Fable 5.1 at `high`/`xhigh`) working directly in `COMFYUI_STORY_HANDOFF_2026-08-09/local_agent`. This touches `server.py`, `static/index.html`, and possibly `media_queue.py` — real cross-file reasoning about an async job/notification path, not a mechanical edit. Opus 5.5 is the right tier.

## The two things the operator asked for, verbatim

1. "When a user human review step needs to happen, I would like the image and/or video to be displayed in the chat so that I can review it in the GUI and not have to go find it in file explorer."
2. "I also want the agent to announce when generations are done and then bring them up in the GUI so I can review them even when the agent has finished its output."

Read together: (1) is about the common case — a render finishes while the turn is still active, and the still/video should show up as an inline card in the chat, not just a file path in text. (2) is the harder case — a render is still running (or the operator walked away) when the agent's own turn/reply ends, and the operator wants the GUI to surface the finished media and actively flag it as done, without needing to ask the agent anything.

## Part 1 — a confirmed, scoped bug: batch renders never produce an inline card today

The GUI already has a full, working inline-media system. Don't build a new one — the gap is narrower than it looks.

**What already exists and works, read directly from source, not inferred:**
- `static/index.html:707` — `mountMediaArtifact(host, art)`. Fully built: handles `art.status` of `pending`/`running`/`timeout`/`error`, fetches the real bytes from `/api/generated_media`, handles 404 (file missing) and 409 (file changed on disk — a real, already-handled race condition), renders an `<img>` or a `<video controls>` with duration, and an "Open containing folder" button wired to `/api/reveal_story_image`.
- `static/index.html:882` — during an active SSE stream, `ev.kind==='media'` calls `mountMediaArtifact(lastMediaHost||b, JSON.parse(ev.data))` immediately, so a card appears live mid-turn.
- `static/index.html:601` — on chat history reload, any stored assistant message with a `media_artifacts` array replays the same cards, so refreshing the page doesn't lose them.
- `server.py:1289-1293` — inside the tool-result loop of an active turn, every tool result is passed to `collect_media_artifacts(name, text)`; anything it returns gets SSE'd out as `kind: 'media'` and also accumulated for storage as `media_artifacts` on the finished message (`server.py:1367`).
- `server.py:123-127` — `STORY_MEDIA_TOOLS = {"story_image_job_status", "render_story_image", "render_story_image_batch", "await_story_image_job"}`, `COMFY_MEDIA_TOOLS = {"comfy_job_status"}`. `render_story_image_batch` is already in that set — the intent to cover it is already there.

**The bug:** `collect_story_media_artifacts()` (`server.py:286`) only understands the *single-job* result shape — it does `manifest = data.get("manifest") if isinstance(data.get("manifest"), dict) else data`, then reads `manifest.get("status")`/`manifest.get("outputs")` off that. That's the shape `render_story_image`, `story_image_job_status`, and `await_story_image_job` each return.

`render_story_image_batch` (`local_agent/tools.py:2509`) returns a completely different, aggregate shape: `{"batch": true, "total": N, "completed": [...], "failures": [...], "pending": [...], "review": {...}, ...}` — no top-level `manifest`, no top-level `status`, no top-level `outputs`. Each *individual* finished job's data (including its own `manifest`/`outputs`) is nested one level deeper, inside `completed[i]`.

Trace it through `collect_story_media_artifacts` with a real batch result: `data.get("manifest")` is absent → `manifest = data` (the whole batch dict). `state = str(data.get("state") or "")` → there is no `"state"` key on a batch result → `""`. `status = str(manifest.get("status") or "")` → no `"status"` key either → `""`. Then: `if not state and not status: return []`. **It returns an empty list every single time**, silently, for every batch render — which is exactly the tool the operator has actually been using for the scene-start stills. This is why nothing has shown up inline: not a frontend gap, a backend parsing gap for one specific, commonly-used tool's result shape.

**The fix:** extend `collect_story_media_artifacts` (or add a sibling `collect_story_batch_media_artifacts` and dispatch to it from `collect_media_artifacts` when `data.get("batch") is True`) to walk `data.get("completed", [])`, and for each entry reuse the exact same per-job extraction logic already written for the single-job shape (each `completed[i]` has its own `manifest`/`outputs`/`story`, in the same shape the existing code already parses correctly) — building one artifact per output file, same as today. Also decide, deliberately, what (if anything) to do with `data.get("failures", [])` and `data.get("pending", [])` entries — probably nothing needs to render for those (no file exists yet), but a `pending`/`error` status card for a failed job could reuse the same `art.status` states `mountMediaArtifact` already handles gracefully, if that seems useful; don't feel obligated to add it if it complicates the fix for no real benefit.

**Testing:** there's no existing test file specifically for `collect_media_artifacts`/`collect_story_media_artifacts` that I found in the time available — check for one (`grep -rn "collect_story_media_artifacts\|collect_media_artifacts" local_agent --include="*.py"`, but see the grep-scoping warning at the bottom of this doc) before assuming none exists. Either way, add a unit test that feeds a real `render_story_image_batch`-shaped result (completed + at least one failure, to match the operator's actual recent runs) through `collect_media_artifacts("render_story_image_batch", <that JSON>)` and asserts it returns one artifact per completed output, not `[]`. Then verify live: run an actual small batch (2-3 jobs) through the real GUI and confirm cards appear for each completed still as the batch finishes, not just a text summary.

## Part 2 — announcing completion after the turn has already ended (the harder, less-verified part)

This is genuinely open — I ran out of investigation time before confirming the key fact that determines the design, and hit a `grep` timeout scanning `local_agent` unscoped (see the note at the bottom) right as I was about to check it. **First thing to establish:** do the pid-based background jobs started by `render_story_image`/`render_story_image_batch` (tracked via a pid + log file, polled by `await_story_image_job`/`story_image_job_status`) ever get registered into the *separate* `media_queue` module/job system that already powers the queue dropdown? Check `local_agent/tools.py` for any `import media_queue` / `media_queue.enqueue(...)`-style call near `render_story_image`'s launch path, and check `media_queue.py` itself for what registers a job into it.

Why this matters — two different starting points depending on the answer:

- **If story-image jobs already register into `media_queue`:** there's real leverage already built. `static/index.html`'s `refreshQueue()` (~line 1001) already polls `/api/media_queue` on an interval *independent of any active turn* (confirm the actual `setInterval(refreshQueue, ...)` call and its period), and `restampQueuedFromQueue()` (~line 1029) already detects a job's transition into `done`/`failed`/`cancelled` and updates a status stamp on that job's existing DOM element. The gap is narrower than it sounds: extend `restampQueuedFromQueue` (or add a sibling function called from the same poll) so that on a transition into `done`, instead of only restamping, it also builds the `art` object for that job's output (same shape `mountMediaArtifact` expects — reuse `collect_media_artifacts`'s server-side logic, exposed via a small new `/api/media_queue`-adjacent endpoint or embedded directly in the `/api/media_queue` response) and calls `mountMediaArtifact()` to actually render the image/video, appended into the chat log as a new card — not just a text stamp — even though no turn is currently streaming. This also needs a place to put that card: if the job's original placeholder element no longer exists (e.g., the operator started a new chat, or reloaded), decide whether to append it to the currently-open chat's log (if the job belongs to that chat) or skip silently; don't guess without checking how job-to-chat association is tracked today.

- **If story-image jobs are NOT in `media_queue` today** (they might be entirely separate — pid+log on disk, only checked on-demand by `await_story_image_job`): this needs either (a) registering them into `media_queue` at launch time so the existing poll/queue-dropdown infrastructure picks them up for free, which is almost certainly the smaller, more consistent change, or (b) a second, parallel client-side poll against `story_image_job_status` for any job the operator is currently waiting on. Prefer (a) unless there's a concrete reason `media_queue` can't represent this job type (check what fields it requires before assuming it can't).

**The "announce" half specifically** (not just "eventually visible if you happen to scroll up"): the operator said "even when the agent has finished its output," which reads as: they may not be looking at the tab at all when it completes. Whatever mounts the media card on completion should also do something that gets attention without the operator having to be staring at the window — a few options, roughly in order of how much they'd cost to build here: (1) a lightweight in-page toast/badge plus an updated document `<title>` (e.g., prefixing `"● "` or an unread count) so a backgrounded tab shows something changed; (2) the browser `Notification` API (requires a one-time permission prompt — check whether this GUI already asks for any permissions anywhere, to match the existing UX pattern rather than introducing a new consent flow the operator hasn't seen before); (3) a short audio cue. Don't build all three speculatively — pick the smallest one that actually satisfies "I don't have to be watching," confirm with the operator's actual usage pattern if it's unclear (this is a desktop app on their own machine, likely with the tab often in the background — a title change plus at minimum a toast is probably the right minimum bar), and leave room to add the others later rather than over-building this in one pass.

## A scoping note, and a real gotcha I hit

Don't treat this as one big feature — land Part 1 first (it's small, concrete, and independently valuable: it fixes inline rendering for every batch render from today onward, which is most of what the operator has actually been running). Part 2 is real but needs the `media_queue` investigation above before any code gets written, so don't start editing `index.html`'s polling logic until that's confirmed one way or the other.

**Gotcha:** an unscoped `grep -r` (or `find`) across `local_agent` without excluding `local_agent/vendor` reliably times out or throws a wall of `Permission denied` — that subtree has restricted-permission directories (`vendor/RNS`, `vendor/LXMF`, `vendor/CRNS`, etc.) that are slow to walk and inaccessible anyway. Always scope with something like `grep -rn "<pattern>" local_agent --include="*.py"` piped through `grep -v vendor`, or better, pass explicit `--exclude-dir=vendor`, and prefer `-maxdepth` with `find`. This bit me mid-investigation on this exact task.
