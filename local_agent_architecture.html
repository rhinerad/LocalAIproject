How the Local Agent Works

A map of local_agent/ as it actually stands today — one request's journey from "you typed a message" to "you got an answer," and the systems standing around that path.

Current priority: this is a general-purpose desktop assistant first. Equal Shares (the film project) is one optional, currently paused specialist mode it can load into — not what it's for by default.
core turn path model backends tools memory & retrieval safety / sandboxing storage & separate pipelines

1 · How a message actually travels

1 server.py

A small standard-library HTTP server bound only to 127.0.0.1:8760 — nothing on the network can reach it except this machine (or a paired phone over its own separate bridge). It streams the reply back token-by-token over Server-Sent Events, so the GUI can show words appearing live instead of waiting for the whole answer.

2 agent.py — the turn loop

This is the actual brain of the request handling, not the language model itself. For every message it: runs safety/scope checks first, gathers whatever context is actually relevant (not everything, on purpose), asks router.py which backend gets this turn, streams the model's response, and if the model asked to use a tool, runs that tool and gives the result back to the model for another pass — up to 6 rounds before it's forced to just answer with what it has.

Today's fix lived here: a safety check that was supposed to catch the model falsely claiming it already did something was instead triggering on ordinary "I will do X" phrasing and replacing perfectly good answers with a confusing refusal. Narrowed so it only catches genuine false claims.

2a The agentic loop, in detail (loop engineering)

This is the part in the diagram bounded by the dashed blue box. It is deliberately a bounded, deterministic loop rather than "keep calling the model until it feels done": each pass (a hop) starts with router.py re-deciding the backend from scratch (the GPU could have become busy mid-conversation), then the chosen model generates one turn, then a fixed check asks one question — did that output contain a tool call? If yes, tools.py runs the exact named tool, the result is appended to the conversation, the hop counter increments, and control returns to the top of the loop for another pass. If no, the model's text is the final answer and the loop exits immediately.

The loop is capped at 6 hops. If the model is still asking for a tool at hop 6, the loop exits anyway and whatever text exists becomes the answer — a runaway "let me just check one more thing" chain can't turn into an unbounded chain of GPU calls. This is the actual mechanism behind "the agent used a tool and then answered": it's not one big reasoning step, it's this small loop running two, three, sometimes six times per message, each time re-checking GPU state and re-picking the model before doing anything.

Re-deciding the backend on every hop, not once per message, is why a render can start midway through a long tool-using answer and the very next hop will already have moved to the CPU model instead of fighting the render for the card.

New (2026-08-31): a third way to exit the loop. Until now the only exits were "no tool call" and the 6-hop cap. Nothing noticed if the model called the exact same tool with the exact same arguments and kept getting an error — it could burn all 6 hops retrying something that could never succeed. Now the last 3 attempts are tracked; if all 3 are the identical tool, identical arguments, and identical failure, the turn stops immediately with a message naming the tool and the error, instead of continuing to hop 6. Verified it does not fire on a tool called with different arguments each time, or on a failure that recovers on a later try.

3 Safety gates, before the model even sees the message

A few things are decided by fixed code, not by asking a small local model to judge correctly every time: refusing help with bypassing a paywall/login/license, keeping old render conversation from leaking into an unrelated request, and handling an exact "stop render" or "start render" command deterministically rather than letting the model guess which tool that means.

4 Context prefetch

Before the model is asked anything, the agent quietly checks: is there an unfinished task from earlier in this chat (a "checkpoint")? Did the operator supply a URL that should be fetched first? Is this question actually about a document in the project? Are there approved past examples worth including? Each of these has its own budget in characters, so one huge tool result can't crowd out everything else the model needs to see.

2 · Where the model actually runs

5 router.py — decide() every single turn

Checked fresh before every reply, not just once at startup: is the GPU idle, or does a render (or something else) already own it? Three independent signals are checked (a render-queue lock file, whether ComfyUI's port is listening, and actual VRAM usage), and if even the GPU-check tool itself fails to run, the router assumes the GPU is busy rather than risk a conflict.

Based on that, it hands the turn to one of three places:

5a GPU Ollama — the good case

When the card is free, a bigger local model (Huihui Qwen3 14B) answers here. There's also an optional, manually-installed 20B model ("Heretic") a person can pick for one chat — it's GPU-only and will refuse rather than quietly switch to something smaller.

5b CPU Ollama — the safe fallback

The moment a render (or anything else) claims the GPU, new chat turns move to a smaller model on four CPU threads instead — slower, but it never fights the render for the card, and it actively evicts its own GPU model rather than leaving it loaded uselessly.

5c PowerInfer — opt-in, experimental, not production yet

A newer, separate backend for a sparsity-accelerated model. It's GPU-only, text-only (no native tool calling yet), and the router will only offer it when its own server process is already running — it never starts or stops that process itself. As of today there's no model that's actually passed a real quality review, so this exists in the picker but isn't a working option to rely on yet.

3 · What the model is allowed to actually do

6 tools.py — a fixed whitelist, not a shell

The model never runs an arbitrary command. It can only call a small set of named, pre-built actions: reading/writing files, running code in an isolated sandbox, searching or fetching the web, analyzing an attached image/audio/video, controlling Sonic Pi for live music, or starting a guarded batch render. Anything not on this list simply doesn't exist to the model.

New (2026-08-31): read_artifact. A tool result too large to fit the context budget is stored in full locally and replaced with a pointer (artifact_id=...) — but until now nothing could ever resolve that pointer back into text; it was a dead end by design (the code's own comment called it "future purpose-built retrieval"). read_artifact closes that: given an artifact id, it returns one bounded slice of the original text plus a next_offset to page through the rest. It's a deliberate paging read, not an automatic re-inject, so the model always knows exactly how much of a large result it has actually seen.

7 The sandbox (run_code)

Every piece of code the model wants to run gets its own throwaway folder. It can't see the rest of the project, can't reach the network unless explicitly allowed, and is capped on time and output size. This was the actual bug fixed today: a script using Python's pathlib could read or write files completely outside that folder, bypassing the intended wall. Fixed with a lower-level enforcement hook that can't be sidestepped the same way, with tests added for the exact gap.

4 · What sits alongside the main loop

8 Memory & retrieval

Conversations persist as individual JSON files. Separately, there's a small local vector database (Chroma) for operator-approved reusable examples, a plain-English "operating memory" file for stable facts and preferences, and a keyword search index over the project's own documentation — so the agent can look something up instead of guessing.

9 Media watcher

Vision and speech-to-text models are not loaded at startup. They only spin up when there's an actual image, video, or audio job waiting, and they release the GPU again as soon as that batch is done — so an ordinary text chat never pays for a model it isn't using.

10 Phone bridge

An explicitly paired phone can chat with the agent over a private radio/Wi-Fi bridge (Sideband/Reticulum), never over the open internet. Anything beyond reading and simple tools — writing files, running code, starting a render — is denied by default until the desktop operator grants that exact permission to that exact device.

11 Worker farm — Mac spoke over WireGuard

Lives in local_agent/worker_farm/. Redis still listens only on this PC (127.0.0.1:6379); a registered Task Scheduler job \local-agent-tunnel-relay (logon trigger, user rhine) publishes that port on the WireGuard hub at 10.90.90.1:6379. That listener is no longer a manually-started process. On the Mac, Ollama and the Celery worker are system LaunchDaemons com.local-agent.ollama and com.local-agent.celery-worker, running as rhineduran / uid 503 — not user LaunchAgents, and they do not wait for a GUI login. Bringing WSL/Docker up so Redis can exist after a cold boot is a separate S4U BootTrigger task \local-agent-wsl-docker-boot under rhine (now a local Administrator). That task is registered; it has not yet been proven across a delayed-login reboot. Live chat turns do use this farm: summarize and embed can run on the Mac, with a local fallback if it doesn't answer. Distilling old chat exports is still a separate workstation-only queue.

The farm routing picture (queues, fallback, what agent.py actually calls) lives in docs/ARCHITECTURE.md. This page is the GPU/CPU visual plus the persistence owners as they stand today.

12 Equal Shares specialist mode

A large, project-specific reference (film production rules, voice pipeline, render safety rules) that only gets loaded into the conversation when a message unmistakably names Equal Shares, a clip ID, or one of its specific terms. Otherwise the agent behaves like an ordinary assistant. Its actual render pipeline is explicitly paused right now by operator decision — this mode is preserved, not deleted, for whenever that changes.
