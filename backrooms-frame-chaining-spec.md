# Build spec: chain video continuity instead of a fresh FLUX still per clip

**For:** a Claude Code session working directly in `COMFYUI_STORY_HANDOFF_2026-08-09`.
**Effort:** Opus 5.5 at `xhigh` (or Fable 5.1 at `high`/`xhigh`) is the right tier for this — it touches four modules and needs careful reasoning about render-path branching, not a mechanical edit.

## The problem

`batch_run_backrooms_gvd.py` currently renders a brand-new FLUX still for the start frame of *every* clip, unconditionally — 102 renders for a 102-clip pack. Most of those clips are the camera continuing in the same scene, not cutting to a new one. The fix: chain the actual last frame of the previous clip's rendered video forward as the next clip's I2V start frame, and only render a fresh still at a real scene change (or when a character re-enters after being offscreen, where chaining risks a drifted/wrong appearance).

## You are not building this from scratch — you're wiring together three things that already exist and are currently disconnected

1. **The decision logic already exists, fully designed, in `work/scene_reasoner.py`.** Its LLM prompt (`~line 197-220`) already asks for exactly this decision, per shot:
   - `continuity_source: "context_video"` — chain the actual last rendered frame/video of the immediately preceding shot, because the scene hasn't changed and no character needs a fresh reference.
   - `continuity_source: "reference_image"` — render a fresh reference still instead, because either the scene changed, *or* a character in this shot last appeared earlier than the immediately preceding shot (so chaining risks that character's drifted appearance) — in which case `reference_character_ids` names who.
   - `continuity_source: "none"` — not a continuity-sensitive shot at all.
   - This is a better, more nuanced version of the naive "chain unless scene change" rule — it already accounts for the character-reappearance drift case. Don't reinvent this logic; use it.
   - **Important caveat:** `scene_reasoner.py` is currently disabled and unwired from any render path (confirmed earlier this session, and fixed for correctness — validated LoRA/character IDs, honest eviction reporting — but never enabled). Wiring it in is a trust decision, not just a plumbing change: it's an LLM making a per-shot call that changes what gets rendered. Treat enabling it as its own sub-step with a dry-run/shadow mode (see Testing below), not a silent flip.

2. **The mechanism to actually use a specific image as the start frame already exists.** `generate_video.py`'s `submit_comfy()` (line ~461) already accepts `start_frame_path` and `end_frame_path` kwargs and wires them straight into the render example (`example.start_frame_path` / `example.first_frame_path`). `batch_run_backrooms_gvd.py`'s current call to `submit_comfy()` just never passes them. The plumbing is there; nothing feeds it.

3. **There's a proven, working ffmpeg/ffprobe pattern to adapt for frame extraction.** `dspy_optimizer.extract_eval_frames()` (line 779) already does `ffprobe` for duration + `ffmpeg -ss <sec> -frames:v 1 -c:v png` for single-frame PNG extraction, used today for VLM QA sampling. Write a small sibling function, e.g. `extract_last_frame(video_path: Path) -> Path`, using the same subprocess pattern but seeking to `duration - epsilon` instead of uniformly sampling. Don't write new ffmpeg-invocation code from scratch; copy the proven pattern (same `creationflags=subprocess.CREATE_NO_WINDOW` handling, same timeout/error handling).

4. **There's a fourth, *related but different* piece — don't conflate it with this.** `local_agent/backrooms_prompt_adapter.py`'s `apply()` already computes a `references` field per clip (`{"start": "{previous_clip_id}_approved_last_frame", ...}`) — an earlier, simpler, non-LLM attempt at similar intent. Nothing reads it today either. Once `scene_reasoner`'s richer decision is wired in, decide explicitly whether `references` should be retired (to avoid two divergent, disagreeing continuity mechanisms) or kept as a fallback default for packs/paths that don't go through `scene_reasoner`. Pick one; don't leave both silently half-wired.

5. **Also distinct, also don't conflate:** `local_agent/PATCH_minimax_ref2vid.md` describes a *staged, never-applied* mechanism for conditioning C002+ on C001's still + locked voice via `MiniMaxH3ReferenceToVideo` — that's identity/voice consistency across the *whole story*, not moment-to-moment visual continuity within a scene. These are complementary, not competing, concepts. Worth a one-line decision on how they'd interact if both are ever enabled, but don't merge the implementations.

6. **The current production graph has no img2img path and no upscale node — the reset checkpoint (below) needs new graph work, not just Python wiring.** I checked `local_agent/graphs/flux_minimax_i2v_api.json` directly: node `5` (`EmptyFlux2LatentImage`) always builds a blank latent from scratch — there's no `LoadImage`/`VAEEncode` path anywhere in this graph today, and no upscale-model node either. Also worth knowing: `EmptyFlux2LatentImage` and the `MiniMaxH3ImageToVideo` node are both already set to 1280×704 — the still and the video input already match in resolution, so there's no size gap to fix. The reset checkpoint's job is de-artifacting/refining a compressed video frame, not upscaling for size.

## Implementation plan

1. **`extract_last_frame(video_path: Path) -> Path`** — new helper (put it next to `extract_eval_frames` in `dspy_optimizer.py`, or a new small module if you prefer separation of concerns). Reuse the ffprobe-duration + single-frame ffmpeg pattern. Output convention: match the existing `runtime/dspy_opt/eval_frames/` naming style (stem + content digest) so it's consistent with what's already there; put it in a clearly-named sibling dir, e.g. `runtime/gvd_backrooms_batch/chain_frames/`.

2. **Wire `scene_reasoner.reason_about_shot()` into `batch_run_backrooms_gvd.py`'s per-clip loop**, before the still/video submission for each clip (index > 0). Run it in **shadow mode first**: log what it *would* decide (`continuity_source`, `continuity_reason`) without actually changing render behavior, across a full pack, and have a human spot-check a sample of the decisions against the actual pack content before flipping it to load-bearing. This directly follows the audit's original guidance that `scene_reasoner` "remains disabled and unwired... its fixes only make it safer to consider enabling later" — this is that "later," but it should still be a deliberate, reviewed flip, not silent.

3. **Branch the render step on the decision:**
   - `continuity_source == "context_video"` **and** the consecutive-chain counter is below the reset ceiling (see step 5): skip the FLUX still render for this clip's start frame entirely. Call `extract_last_frame()` on the *previous* clip's already-rendered video, pass the result as `start_frame_path` to `submit_comfy()`.
   - `continuity_source == "context_video"` **and** the chain counter has hit the reset ceiling: run the refine-checkpoint path instead (step 5) rather than either plain passthrough or a fresh independent still.
   - `continuity_source == "reference_image"` (or `"none"`, or clip index 0, or `scene_reasoner` unavailable/low-confidence/`needs_operator_input`): render a fresh FLUX still as today. Fail toward the current (safe, already-proven) behavior on any ambiguity — this should never be the path that silently does the wrong thing.
   - Log the decision and its reasoning into `progress.json` per clip (mode used, source clip id if chained, `continuity_reason`) — this is the same "make failures diagnosable" principle from the parsing fixes earlier tonight. A future "why does clip C047 look wrong" question should be answerable from the progress file, not from re-deriving it by hand.

4. **Track a consecutive-chain counter per continuous run**, reset to 0 whenever `continuity_source` is `reference_image`/`none` (a real cut happened) and incremented each time a clip chains via `context_video`. This is what step 3's reset-ceiling check reads.

5. **Build the refine-checkpoint path — this is the actual answer to "how do we extend a chained scene past N clips without either compounding drift or breaking continuity with a hard cut."** Chaining many clips in a row off raw extracted MP4 frames compounds compression artifacts and slow drift (on top of the character-reappearance case `scene_reasoner` already catches). The fix is **not** a fresh independent FLUX generation (that discards the pose/composition/blocking continuity that's the whole point of chaining) and **not** a plain super-resolution upscale alone (an upscaler sharpens/hallucinates detail from whatever's already there — it doesn't correct color drift or identity wander, and per point 6 above there's no resolution gap to fix anyway). It's a **low-denoise img2img regeneration of the actual extracted last frame**, conditioned on the same character LoRA(s)/prompt that generated it originally:
   - New graph branch needed (see point 6 above — nothing like this exists in `flux_minimax_i2v_api.json` today): `LoadImage` (the extracted last frame) → `VAEEncode` → `KSampler` at a **low, tunable denoise** (start around 0.2–0.35 — low enough to preserve pose/composition/identity, high enough to actually clean up compression softness and reset accumulated drift; treat this as an empirically-tuned named constant, not a guess baked in once and forgotten) → optionally a sharpen/upscale-model node afterward if the refined output still looks soft. Confirm what upscale custom nodes are actually installed in the real ComfyUI instance before assuming one (e.g. "Ultimate SD Upscale") is available — don't assume from this repo's checked-in graph alone.
   - Use the refined output as the `start_frame_path` for the next clip, and reset the consecutive-chain counter to 0 (this clip becomes the new "clean anchor" the chain counts from).
   - Pick the reset ceiling (N consecutive chained clips) as a named, tunable constant, not an implicit accident of whatever `scene_reasoner` happens to decide.

## Testing

- **Offline, mocked:** unit tests (new or extend `test_batch_run_backrooms_gvd.py`) covering: `context_video` decision skips the still render and passes the right `start_frame_path`; `reference_image`/`none`/clip-0/low-confidence all fall back to a fresh still; the consecutive-chain counter increments/resets correctly and actually routes to the refine-checkpoint path once it hits the ceiling; `progress.json` records the decision (including which mode — passthrough chain vs. refine checkpoint vs. fresh still) correctly.
- **Shadow-mode dry run:** run `scene_reasoner` decisions across the real 102-clip pack without changing render behavior, and manually review a sample (particularly any clip flagged `reference_image` due to character reappearance) before trusting it live.
- **Refine-checkpoint denoise tuning:** before trusting the reset ceiling on a long chain, do a small live comparison at a couple of denoise values (e.g. 0.2 vs. 0.35) on one actual chained-and-drifted frame, and visually confirm the result still reads as the same character/pose/scene rather than a subtly different regeneration — too high a denoise defeats the point (it becomes a fresh generation wearing a continuity costume), too low doesn't actually clean anything up.
- **Small live test before a full run:** 3-4 consecutive clips within one scene, confirm the 2nd/3rd/4th clips actually skip the FLUX still and visually continue from the prior clip's last frame, and that at least one deliberate scene-change clip still gets a fresh still. Don't go straight from unit tests to a full 102-clip live run — that's the exact gap (green tests, untested live behavior) that let the SDXL-default issue from earlier tonight hide as long as it did.
